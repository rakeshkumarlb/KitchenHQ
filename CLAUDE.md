# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

KitchenHQ is three independently deployable services orchestrated by the root `docker-compose.yml`:

| Service | Dir | Language | Port | Role |
|---|---|---|---|---|
| `dbmcp` | `dbmcp/` | Python (FastAPI + FastMCP) | 18000 | Owns the SQLite database. Exposes the same data operations twice: as plain REST (`/api/*`) and as MCP tools (`/mcp`, via `mcp.streamable_http_app()` mounted on the same FastAPI app). |
| `chatui` | `chatui/` | React (Vite) + Python (FastAPI) | 8080 | React SPA built to `chatui/dist` and served by a FastAPI backend that proxies CRUD calls to `dbmcp` and chat/automation calls to `agent-api`. Holds no LangChain/MCP dependency itself. |
| `agent-api` | `agents/` | Python (LangChain + FastAPI) | 8090 | The only process that talks to the LLM and to `dbmcp` over MCP. Serves `/chat` and `/invoke/{job_name}` for `chatui`, and runs the same 8 cron jobs internally via an in-process `AsyncIOScheduler` — one process, one place that owns (and disposes) model/MCP connections. `cli.py` run standalone gives an interactive terminal REPL with the Executive Chef, independent of this service. |

There is no top-level package manager tying the three together — each has its own `requirements.txt` (Python, pinned) or `package.json` (Node). The one piece of genuinely cross-service code is `shared/constants.py` (day / meal-type vocabulary + ordering); since each service builds from its own Docker context, `shared/sync.py` vendors a byte-identical copy into `dbmcp/constants.py` and `agents/app/constants.py` (edit `shared/`, run the script; `--check` / a `dbmcp` test guard drift), and chatui reads the same values at runtime from the `constants` block in `GET /api/dashboard`. See `shared/README.md`.

Every service requires `KITCHENHQ_API_KEY` to be set (see Commands) — all three refuse to start without it.

**Linting/formatting are not configured anywhere in this repo** (no ESLint/Prettier config, no `pyproject.toml`). `dbmcp` has pytest smoke tests (`dbmcp/tests/`); `chatui` and `agents` have none.

## Commands

### Full stack (Docker Compose, from repo root)
```powershell
docker compose up --build
```
Starts `dbmcp` (18000), `agent-api` (8090), and `chatui` (8080). Requires a root `.env` (copy from `.env.example`) with `KITCHENHQ_API_KEY` set — `docker-compose.yml` fails fast via `${KITCHENHQ_API_KEY:?...}` if it's missing. `agent-api` also reads `agents/.env` (copy from `agents/.env.example`; set `OPENAI_API_KEY` or `LLM_PROVIDER=ollama`, and the same `KITCHENHQ_API_KEY`).

To run a subset: `docker compose up --build dbmcp chatui`.

Set `KITCHEN_DB_HOST_PATH` in root `.env` to relocate the SQLite volume (defaults to `./data`). `KITCHEN_TIMEZONE` sets the scheduler's `TZ` (default `Asia/Kolkata`).

### dbmcp, standalone
```powershell
cd dbmcp
pip install -r requirements.txt
$env:KITCHENHQ_API_KEY = "..."
python init_db.py            # runs uvicorn on :18000, creates/seeds kitchen.db on startup
```
Or via its own Dockerfile: `docker build -t kitchenhq-db-mcp .` then `docker run --rm -p 18000:18000 -e KITCHENHQ_API_KEY=... -v "${PWD}/data:/data" kitchenhq-db-mcp`. Every request (REST and MCP) needs an `X-API-Key: <KITCHENHQ_API_KEY>` header.

Tests: `pip install -r requirements-dev.txt && pytest tests/` (spins up a temp SQLite DB per test via `KITCHEN_DB_PATH`, no live server needed).

Backups: `python scripts/backup_db.py` snapshots the live DB into `backups/` (uses SQLite's online backup API, safe under concurrent writers), keeping the last 14 by default — see `dbmcp/README.md` for scheduling it.

### agents (agent-api), standalone
```powershell
cd agents
pip install -r requirements.txt
python cli.py                                          # interactive terminal chat, no server
python -m uvicorn app.server:app --host 0.0.0.0 --port 8090   # chat/invoke API + cron scheduler
```
Requires `dbmcp` reachable at `MCP_URL` (default `http://localhost:18000/mcp` when run outside Docker; the Docker Compose network uses the service name `dbmcp`) and `KITCHENHQ_API_KEY` matching `dbmcp`'s.

### chatui, standalone
```powershell
cd chatui
npm install
npm run dev          # Vite dev server; the FastAPI backend below must run separately for /api/* to work
npm run build         # outputs chatui/dist, which app.py serves as static files
```
```powershell
cd chatui
pip install -r requirements.txt
$env:KITCHENHQ_API_KEY = "..."     # AGENT_API_URL/DB_API_URL default to the Docker service names
python -m uvicorn app:app --host 0.0.0.0 --port 8080
```
On first load the browser prompts for the access key (same `KITCHENHQ_API_KEY` value) and stores it in `localStorage`; a 401 from any `/api/*` call clears it and re-prompts.

## Architecture

### dbmcp is the single source of truth for the schema
The DDL lives in `dbmcp/schema.sql` — a fresh-start `CREATE TABLE IF NOT EXISTS` script with **no in-place migration** of older layouts; a database is assumed to start empty or already be on the current schema. `dbmcp/db_design.md` documents the same tables for humans — keep it in sync when changing `schema.sql`, but if the two ever disagree, `schema.sql` is authoritative. `kitchendb/schema.py`'s `initialize_database()` runs that script and seeds a fresh DB (`kitchendb/seed.py`), called on FastAPI `lifespan` startup. The data operations live in `kitchendb/tools/*.py` as plain functions decorated with a local `@tool` (`kitchendb/tools/registry.py` just collects them; `kitchendb/server.py`'s `build_mcp()` adds each one to a fresh `FastMCP` instance built per app), and `kitchendb/routes.py` re-exposes almost every one of them as a thin Pydantic-validated FastAPI REST route that calls the same function. `dbmcp/init_db.py` is now only a compatibility shim (`uvicorn init_db:app`, the `python init_db.py` dev runner) re-exporting from the `kitchendb` package — the implementation itself is not in that file.

Two write paths follow a propose-then-acknowledge pattern: the propose step never touches `inventory`, and the acknowledge step is idempotent via a required `acknowledgement_key` recorded in `inventory_transactions.idempotency_key`. The two flows' replay response shapes differ, though: shopping's `acknowledge_shopping_items` returns `{"replayed": True, ...}` on a repeat call (see below), while prep's `capture_prep_completion_status` just returns the unchanged row with no `replayed` flag - both are idempotent, but check `status`, not a `replayed` key, to tell a prep replay from a first-time acknowledgement. Preserve idempotency (not the exact response shape) when extending inventory-affecting flows.
- **Prep**: `add_detailed_prep_schedule(detailed_instructions: list[str], ingredients_used: list[{item_name, quantity, unit}])` stores both as validated JSON on the row (`status='assigned'`, `created_at` stamped) — this is the *only* place the agent supplies what a task will consume (matched by `item_name`, never `inventory_id`, since the caller can't reliably know one ahead of time). There is no separate acknowledge endpoint or step for prep: `capture_prep_completion_status(is_completed=True)` is the *one* human action ("check this task off"), and it always deducts whatever `ingredients_used` holds - `completed` and `acknowledged` are not two stages of that action, they are its two possible outcomes, decided purely by whether `ingredients_used` was non-empty at creation time: empty → `status='completed'` (nothing to deduct, so still reopenable), non-empty → `status='acknowledged'` (something was deducted, key `prep-<id>-complete`, locked against reopening because undoing a real deduction isn't safe to automate). Both mean the same thing to the household - "done" - and both land in the same "recently completed" bucket everywhere (dashboard, `get_prep_schedules`, chatui's Task List); the only place the distinction matters is that an `acknowledged` row rejects a later `is_completed=False` call (400) while a `completed` one does not. Prep deduction deliberately does **not** guard on stock levels — `inventory.quantity` and `inventory_transactions.quantity_after` have no `>= 0` CHECK in `schema.sql`, so a deduction always applies and can leave a negative balance that stays visible until a shopping run. A task still `'assigned'` more than 2 hours after `created_at` is stale: `expire_stale_prep_tasks()` (MCP tool, no REST route) flips it to `status='expired'` — never touching inventory — and both `capture_prep_completion_status` and `cancel_prep_schedule` then reject it (400), the same way they reject an already-`acknowledged` row. The `expire_prep_tasks` job (role `sous_chef`, every 2 hours — `agents/app/scheduler.py`) is the only caller; it's a deterministic housekeeping sweep, not a planning decision.
- **Shopping**: there is no "shopping list" entity — `shopping_items` alone *is* the one pending list, unique on `item_name` (`COLLATE NOCASE`). `add_shopping_items` is an `INSERT … ON CONFLICT(item_name) DO UPDATE` upsert (merges `proposed_quantity`), so callers (agent or human) never choose between creating vs. appending — `edit_shopping_item`/`delete_shopping_item`/`clear_shopping_items` round out add/edit/delete/clear. `acknowledge_shopping_items` (REST-only, not an MCP tool — a human action, not an agent one) matches each purchased item to `inventory` by `item_name`, adds the actual quantity, and **deletes** the `shopping_items` row (that's what "clears" it) — since the row is gone on replay, idempotency is checked directly against `inventory_transactions.idempotency_key` (`{acknowledgement_key}:{shopping_item_id}`) instead of a status flag.

Email is **agent-driven, not automatic**, and it lives entirely in `agent-api` — `dbmcp` has no SMTP config, no `send_*_email` tools, and no `/api/notifications/*` routes. `agents/app/email/` is a one-responsibility-per-module package: `schemas` (Pydantic `*Request` payload contracts + day/meal vocab), `smtp` (transport + recipient resolution — reads `user_profile` over `GET {DB_API_URL}/api/profile`, never SQLite), `render` (each builder returns `(subject, text_body, html_body)`; `parse_lines` turns a `weekly_menu` JSON-array field or legacy string into a line list), `backfill` (fetch the saved menu from `GET /api/dashboard` for `send_weekly_plan_email` when `days` is omitted — the only email data-read left besides the recipient), `tools` (`make_email_tools(settings)` → the three `StructuredTool`s `send_prep_task_email` / `send_weekly_plan_email` / `send_shopping_list_email`, same names/params/docstrings the prompts already use). `kitchen_agent.run_agent` appends them to every run's toolset right after `get_job_context`, same per-request lifetime. Each returns `{"sent": bool, "skipped"?: str, ...}` and never raises — a disabled `notify_on_task_creation`, an unset `SMTP_HOST`, or an SMTP failure all come back as `{"sent": false}`, so a job never fails on email; an invalid payload *is* rejected (and `send_shopping_list_email` now rejects an empty `items`). Only `send_weekly_plan_email`'s `days` is optional — back-filled from the saved menu, since that email summarizes a whole week and sending it isn't an enforced job step; the prep and shopping-list emails take the plan/list the agent just authored and only render + send it. Recipient resolution (`user_profile` → `email`/`cc_emails`/opt-out) stays in `smtp` server-side — the model never picks the address. `SMTP_*` env is on the `agent-api` compose service. The role prompts (and `app/jobs.py` job prompts) tell each role to send the matching email whenever it saves a prep schedule / weekly plan / shopping list.

`household_members` (`id`, `name`, `dietary_preferences` JSON array, `health_conditions` JSON array) holds individual household members — CRUD is REST-only (`/api/household-members`, edited by a human on the Profile page, not an agent tool), and the row set is embedded in `GET /api/dashboard` as `household_members`. The `get_household_preferences` MCP tool folds these in alongside the free-text chef note (`user_profile.notes`) and `user_profile.favorite_recipes` (JSON, max 10, newest first — a legacy field nothing currently writes to, since the star-rating flow that used to populate it was removed in favour of `household_members`), plus a `has_preferences` bool and a `guidance` line. This tool is the single shared source of household rules/preferences/conditions: the Executive Chef and Sous Chef prompts tell them to consult it before deciding what to cook, and the Food Inspector consults the exact same tool when auditing what they decided — never a duplicated rules file. It's optional context; when it comes back empty (`has_preferences: false`, what a fresh install returns) every role proceeds anyway.

The **Food Inspector** is a fourth agent role, an LLM-as-judge: it never plans a menu or a prep task, only scores decisions the Executive Chef and Sous Chef already saved. `weekly_menu` and `detailed_prep_schedule` each carry `score` (0–100) and `audit_feedback` (text) columns — `NULL` means not yet audited, and chatui's Weekly Menu and Task List pages surface both. `add_weekly_menu_item` resets a slot's `score`/`audit_feedback` to `NULL` on every upsert (a re-planned slot is a new decision awaiting judgement); `detailed_prep_schedule` rows are audited once at creation and not reset. Two MCP tool pairs drive it — `get_unaudited_weekly_menu_items`/`record_weekly_menu_audit` and `get_unaudited_prep_tasks`/`record_prep_task_audit` (both filtered on `score IS NULL`; the prep-task pair deliberately **includes cancelled tasks**, since the decision being judged is what the Sous Chef planned, not whether it was performed — contrast with `get_prep_schedules`, which excludes them). Two nightly cron jobs, `menu_audit` and `task_audit` (`agents/app/jobs.py`, role `food_inspector`), each fetch whatever is unaudited and score it against the same `system.md` rules and `get_household_preferences` context the author used; both are also invocable on demand from chatui's Automations page like any other job — new jobs need no explicit Automations wiring since `agent-api`'s `/jobs` lists `SCHEDULED_REQUESTS` dynamically and chatui's `/api/automations/*` proxies whatever that returns. `food_inspector` has its own prompt fragment (`agents/prompts/food_inspector.md`) but, like every role, shares `system.md` verbatim — it is scheduled/automation-only, with no chat persona (its `JOB_RESULT_MODELS` entry, `FoodInspectorResult`, is passed explicitly the same way `weekly_menu`'s `ExecutiveChefResult` is, not registered in `RESPONSE_FORMATS`). Only the "did you check" step is a hard `require_tools` requirement (`get_unaudited_weekly_menu_items` / `get_unaudited_prep_tasks`) — how many rows actually get scored varies run to run, so unlike `weekly_menu`'s 28-slot count it isn't enforced by `JOB_REQUIRED_TOOL_COUNTS`.

`validate_weekly_menu_policy` encodes the household's menu rules (no egg/meat/fish in lunches, five distinct weekday lunches) — call it with **no args** to validate the currently-saved `weekly_menu` table. The `weekly_menu` job builds a week slot-by-slot: 28 `add_weekly_menu_item` upserts (`INSERT … ON CONFLICT(day_of_week, meal_type) DO UPDATE`, guarded by the `UNIQUE` index on `(day_of_week, meal_type)` in `schema.sql`) then `validate_weekly_menu_policy()` and fix-ups. `add_weekly_menu_item` takes `ingredients: list[str]` and `full_recipe: list[str]` (plain-text lines, stored as JSON arrays; the UI/emails render them as `<ul>`/`<ol>`, `parse_lines` handles legacy string rows) and refreshes the row's `updated_at` on every upsert. `run_agent` enforces the full Monday–Sunday week for the `weekly_menu` job via `_weekly_menu_slot_shortfall` — it checks the **distinct** `(day, meal)` args actually saved, not just the call count, so a run that re-saved weekday slots to hit 28 calls while leaving Saturday/Sunday stale is nudged and then fails. The old whole-week `add_weekly_menu_plan` (validate-then-write) function and its `POST /api/weekly-menu/{plan,validate}` routes are gone entirely — removed in the `dbmcp` reorg, not merely commented out — leaving only the per-slot `add_weekly_menu_item` upsert (`POST /api/weekly-menu`) and the standalone `validate_weekly_menu_policy` call.

A `@app.middleware("http")` function (`require_api_key`) sits in front of every route except `/api/health`, checking `X-API-Key` against `KITCHENHQ_API_KEY`. Because it's outer FastAPI middleware, it also covers the mounted `mcp.streamable_http_app()` at `/mcp` — there's no separate MCP-layer auth.

### agents: nothing outlives a single request
`agents/app/` replaces the old single `agent.py` god-file. `app/kitchen_agent.run_agent(role, text, settings, ...)` is the core entry point: it builds a fresh LLM client (`app/llm.build_model`) and a fresh MCP tool set (`app/mcp_tools.load_tools`) for *this call only*, runs the LangChain agent, and disposes the LLM client's underlying HTTP connections (`app/llm.dispose_model`) in a `finally` block before returning. There is no persistent `KitchenHQAgent` instance and no cross-call lock — concurrent calls for different roles/sessions run fully independently. The return value is the model's `structured_response` JSON when a `response_format` is in play, else the final assistant text via `_final_text()` (last non-empty assistant message → recap of tool names). Because Ollama often ignores `response_format` *and* ends a job on a silent tool call, `run_agent` also does a one-shot "reply now in plain text, no more tools" nudge when a job finished its required writes but left no prose and no `structured_response` — so `agent_runs.result` is a real summary, not a tool recap.

This is a deliberate fix for a real incident: the previous code built one LLM client per role and kept it alive for the life of the process (days, in a long-running container). A long-lived Ollama connection would eventually go stale and wedge further requests — sometimes badly enough to affect Ollama access from elsewhere on the machine. Every LLM/MCP connection this codebase opens now has a bounded lifetime of one request or one scheduled job; if you add a new call site, keep that invariant.

Prompts live in `agents/prompts/*.md` (`system.md` is a role-neutral shared base — household context and dietary rules only, no "you are X" identity claim, since every role gets it appended before its own; `executive_chef.md`/`sous_chef.md`/`pantry_manager.md`/`food_inspector.md` are per-role fragments appended as "Your role"). **Division of labour between the two prompt layers:** the role `.md` holds only standing behaviour — identity, lane/boundaries, the standard method the role always follows. Everything job-specific — which day, which meals, the time cap, which email tool with which fields — lives in `app/jobs.py`'s `SCHEDULED_REQUESTS`, each a self-contained `PURPOSE:` line followed by numbered steps. Keep new job detail out of the `.md` files. `app/prompts.system_prompt_for(role, settings)` prepends a one-line `current_context_block` (current date/time in `settings.tz`) that mainly points the model at `get_job_context`. That tool — built per run in `app/job_context.py`, appended to the toolset by `run_agent`, closing over `settings` and the `job_name` `run_job` threads down — is the authoritative source for date math (every reference date carries its weekday name) *and* the intent behind a scheduled run (`JOB_CONTEXT` gives each job a `focus`/`rationale` plus a `menu_scope` that `build_job_context` resolves into `job.target_menu_days` — the exact `weekly_menu` weekday rows the job acts on, since that table is keyed by weekday not date and the model must not do date→weekday arithmetic itself). The cron day/time is deliberately never surfaced (a job can be `/invoke`d any time). Interactive chat gets `run_type: "interactive_chat"`, `job: null`. `zoneinfo` still needs the `tzdata` package on Windows (pinned in `requirements.txt` for `sys_platform == "win32"` — Linux/Docker has it from the OS).

All four roles get the exact same MCP toolset — there is no per-role tool allowlist (`app/mcp_tools.load_tools()` takes no role argument); `run_agent` then appends one locally-built `get_job_context` tool (not from MCP). Role boundaries are enforced entirely by the system prompt telling each role what to stay in its lane on, not by hiding tools; this was a deliberate simplification over the previous `ROLE_TOOLS` filtering, on the basis that it's easy to reintroduce per-role tool restriction later if a role actually misuses a tool it shouldn't. `app/models.py` holds the structured `response_format` models: `SousChefResult`/`PantryManagerResult` are wired per-role in `RESPONSE_FORMATS` (used for both chat and jobs); `ExecutiveChefResult` is **not** in that map — chat with the chef stays free text — and is passed to `run_agent(response_format=...)` only by the `weekly_menu` job (`JOB_RESULT_MODELS`), so that job returns structured JSON instead of relying on the model to emit a closing summary.

`app/jobs.py` holds the canned scheduled prompts (`SCHEDULED_REQUESTS` — self-contained `PURPOSE:` + numbered steps, deliberately silent on which day/time they normally run, since `/invoke/{job_name}` can fire any of them on demand at any time), a `JOB_ROLES` / `JOB_RESULT_MODELS` / `JOB_REQUIRED_TOOLS` / `JOB_REQUIRED_TOOL_COUNTS` map set, and `run_job()`, which passes all of them to `run_agent` (`job_name` becomes the run's `focus`/`rationale`/`target_menu_days`; the explicit `response_format` gives the `weekly_menu` job structured output). `run_agent` compares the tool calls actually made against `require_tools` (must appear at least once) and `require_tool_counts` (must appear ≥ N times — `weekly_menu` needs 28 `add_weekly_menu_item` calls for a full week); on any shortfall it sends up to `_MAX_FOLLOWUPS` corrective "still outstanding: …, do it now" turns and then **raises** — so a job that saved 0 (or 22) of 28 slots is recorded `failed` with the shortfall in the error, not a blank `completed`. **Always pass `trace=False` from `run_job`** — `trace=True` returns a human-readable event transcript, not JSON, and passing it silently broke sous_chef/pantry_manager job telemetry for a while (see below). `run_job` then posts telemetry to `dbmcp`'s `/api/agent-runs` (`app/telemetry.py`) regardless of success/failure. The `result_model.model_validate(...)` check on that structured output is intentionally non-fatal (logs a warning, doesn't raise): Ollama's `create_agent(..., response_format=...)` support is flaky — the model's actual tool calls/DB writes already happened by that point regardless of whether it also managed to produce parseable structured JSON, so a validation miss must never flip a real success into a reported failure.

Chat history is not kept in process memory: `run_agent()` loads/saves each session's message list from/to `dbmcp`'s `chat_sessions` table (`app/history.py`), serializing with `langchain_core.messages.messages_to_dict`/`messages_from_dict`. Scheduled jobs call `run_agent(..., remember=False)`, which skips history entirely — each scheduled run is a fresh one-shot request.

### agent-api: one process, one FastAPI app, an in-process scheduler
`app/server.py` is the single deployable unit that replaces the old `agent-worker` container: its FastAPI `lifespan` starts an `AsyncIOScheduler` (`app/scheduler.py`) that fires the same 8 cron jobs directly in-process (no network hop — it calls `run_job()` the same way the HTTP route does), and it exposes `POST /chat` (used by `chatui`, keyed by session id with a per-session `asyncio.Lock` so only same-session turns serialize), `POST /invoke/{job_name}` (runs one scheduled job on demand — this is what `chatui`'s Automations page calls to "run now" and see the output), `GET /jobs`, and `GET /health`. `cli.py` is a separate, unrelated entry point: a standalone terminal REPL over `run_agent()` for local dev, with no server or scheduler involved.

### chatui is a pure REST client of dbmcp and agent-api
`chatui/app.py` holds no LangChain/MCP dependency and does not import anything from `agents` — `/api/chat` and `/api/automations/*` proxy to `agent-api` (`AGENT_API_URL`, default `http://agent-api:8090`) exactly the way `/api/dashboard` etc. proxy to `dbmcp` (`DB_API_URL`). This is what let `chatui`'s own Docker image drop the shared root `requirements.txt` and build from its own directory with just `fastapi`/`uvicorn`/`httpx`/`pydantic`. `chatui/app.py`'s inventory-mutation proxies (`PATCH /api/inventory/{id}`, `.../discard`) are commented out (no caller) now that the Pantry page is read-only.

`chatui`'s own `/api/*` routes (except `/api/health`) are behind the same `require_api_key` middleware pattern as `dbmcp`, since real users hit them directly from the browser. The React app has a key-entry gate (`src/components/AccessGate.jsx`) in front of everything else in `App.jsx`; `src/services/api.js` attaches the stored key to every request and clears it on a 401.

The React app (`chatui/src`) has no router — `App.jsx` holds `page` in `useState` and switch-renders `Dashboard`/`Pantry`/`WeeklyMenu`/`TaskList`/`Chat`/`Automations`/`Profile`, all fed from one `/api/dashboard` payload fetched on mount and patched locally after each mutation (see `src/services/api.js` for the full REST surface it calls). `Automations` is the odd one out: it fetches its own data from `/api/automations/jobs` and `/api/automations/runs` rather than the shared dashboard payload, and lets a user trigger `/api/automations/invoke/{job_name}` to see a scheduled job's output without waiting for its cron time. `Profile` reads/writes the single `user_profile` row via `/api/profile` (also embedded in the dashboard payload as `profile`); its `name` drives the header greeting and its `email` is where dbmcp sends the "new prep task" notification. `Profile` also renders CRUD for `household_members` via `/api/household-members` (also embedded in the dashboard payload). The dashboard payload also carries a `constants` block (`days`, `meal_types`, and their order maps) so the React app never hard-codes the weekday/meal vocabulary — `WeeklyMenu.jsx` builds its grid from `data.constants`. `WeeklyMenu` and `TaskList` both render a `score`/`audit_feedback` badge per row ("Unaudited" when `score` is `null`) from the Food Inspector's audits.

`Chat.jsx` can list and switch back into recent conversations: `GET /api/chat-sessions` (chatui proxies to a new `dbmcp` endpoint, `GET /api/chat-sessions?limit=5`, that lists the 5 most recently updated sessions ordered by `updated_at` with a preview built from the first human message — it doesn't prune anything, it only limits what's *returned*) and `GET /api/chat-sessions/{id}` (chatui converts dbmcp's raw LangChain-dict messages into the simple `{role, content}` shape the UI renders, dropping tool-call/empty-content messages). Picking a past conversation swaps the browser's stored `session_id` and repopulates the transcript; agent-api's history load/save (`app/history.py`) is unaffected since it always operates on whatever `session_id` it's given.

### Still prototype-grade
No multi-user auth (one shared key for the whole household, not per-user accounts); SQLite with no replication (only local timestamped snapshots via `dbmcp/scripts/backup_db.py`); no CI; `chatui` and `agents` have no automated tests.
